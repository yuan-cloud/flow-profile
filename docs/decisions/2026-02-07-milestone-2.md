# Risk Assessment: M2 Completion (Web Context Builder)

Date: 2026-02-07
Milestone: M2 - Web Context Builder (Vue 3 UI)

## Assumption Check
- Assumed modern browser support only (no IE11, legacy Edge). Users on older browsers will not be supported.
- Assumed Web Worker isolation is sufficient for processing large flows without blocking the main thread.
- Assumed WCAG 2.1 AA baseline covers accessibility needs; manual testing with screen readers not yet performed.
- Assumed three-column layout is appropriate for desktop-first usage; mobile responsiveness is functional but not optimized.
- Assumed 500-node threshold for virtualization is appropriate; not validated against real-world flow distributions.

## Counter-Argument
- A skeptical engineer could argue that the Pinia store structure may not scale if additional features (undo/redo, collaborative editing) are added later.
- Alternative: Could have used a more event-driven architecture (event sourcing) for better debugging and time-travel.
- The Playwright/Bun incompatibility workaround (Node.js wrapper) adds friction to the test workflow and could confuse contributors.

## Risk Scenario
- **Web Worker memory pressure**: Large flows with deep nesting could exhaust worker memory, causing silent failures or crashes.
  - Detection: User reports of blank previews, browser console errors, E2E test failures on large fixtures.
  - Blast radius: Single user session, recoverable by page refresh. No data loss (flows are read-only input).

- **Accessibility gaps**: Automated axe-core testing catches common issues but misses keyboard traps, screen reader announcements, and focus management edge cases.
  - Detection: User feedback from assistive technology users, manual accessibility audits.
  - Blast radius: Affects users with disabilities, potentially violates compliance requirements.

- **E2E test flakiness**: Tests fail intermittently due to UI timing issues ("Context Preview" element visibility race condition observed during 1ci fix).
  - Detection: CI failures on passing code, developer frustration.
  - Blast radius: Slows development velocity, erodes trust in test suite.

## Questions to Reconsider
- Should we add a manual accessibility audit before M5 demo?
- Is the 500-node virtualization threshold backed by performance profiling, or should we measure?
- Should the Playwright Node.js workaround be documented in CONTRIBUTING.md for new contributors?
- Are the E2E test timeouts (30s for "Context Preview") too aggressive or too lenient?

## Tech Debt Flags
- **Playwright/Bun incompatibility**: Requires Node.js wrapper script (`apps/web/scripts/run-playwright.sh`). Documented in `docs/decisions/2026-02-05_222846__playwright-bun-e2e-incompatibility.md`. Revisit when Bun improves Playwright support.
- **Pre-existing lint errors**: `vitest.workspace.ts` has formatting issues not addressed in M2. Low priority but creates noise.
- **axe-core version coupling**: Version 4.8.5+ required for Playwright 1.58.1 compatibility. Future upgrades need coordinated testing.
- **Debug artifacts left in repo**: Several temporary files from 1ci debugging exist but are inert. Cleanup deferred.

## Rollback Plan
- **Web app removable**: The CLI (`packages/cli`) is fully standalone. Removing `apps/web` does not break core functionality.
- **AI adapter optional**: The AI suggestion panel can be disabled/removed without affecting context building.
- **Individual panels removable**: Risk findings, capability inspector, and redaction controls are modular and can be hidden via feature flags if needed.
- **packages/ui extractable**: Reusable components are isolated and could be published separately if the web app is abandoned.
